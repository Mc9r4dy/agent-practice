## 3. 已通过的核心内容

### 3.1 选题符合指导手册

指导手册将 Agent04 的教学定位确定为 SQL 运维、权限管控、SQL 注入攻防、数据库备份恢复和安全基线检查。当前方案以 MySQL 巡检、权限审计、异常 SQL 分析、备份恢复和事件处置为核心，覆盖关系明确。

当前项目应继续归入“基于智能体的网络安全小助手开发—网安专业课情景教学”，附件二属于另一类 AI 安全工具方向，不是本项目立项的必要依据。

### 3.2 符合设计实例的基本结构

方案已包含以下内容：

1. 对应课程内容；
2. 四项核心教学任务；
3. 企事业单位真实业务背景；
4. 学员角色和多分支决策；
5. 失败后果及重新实操；
6. 知识讲解、实操校验和报告生成；
7. 从事件发现到处置复盘的教学闭环。

### 3.3 模拟攻击方案边界清楚

新增的模拟攻击方案采用固定场景和预设证据，只作用于隔离教学沙箱和合成数据；大语言模型不能直接执行 SQL，危险操作由后端接口和规则网关拦截。该设计既能制造可分析的异常线索，又不会把系统建设成真实攻击工具，方向合理。

### 3.4 四项结课成果已有对应关系

开发规划已经映射指导手册要求的四项成果：规划设计方案、功能手册、源代码及数据库压缩包、源代码安全审计报告。后续需要把这些成果纳入具体时间表和验收清单，而不应集中到最后一天补写。

## 4. 开发前必须整改的 P0 问题

### P0-1：第一版范围仍然过大

当前规划同时包含 Vue 前端、FastAPI 后端、SQLite、MySQL 双数据库、Docker Compose、大模型适配、知识检索、十个业务模块、三条任务分支、攻击回放、备份恢复、教师管理、评分和报告。对于 18 个工作日的个人项目，完整实现和稳定演示的风险较高。

**整改要求：**冻结第一版 MVP，只保留一条完整故事线、三个可选择的起始节点、四项必做任务和一份闭环报告。三条分支应复用同一套任务组件和数据，不建设三套独立流程。

建议第一版只实现：

- 场景状态机；
- 固定事件与证据注入；
- 基线巡检、权限审计、日志分析、备份验证四项任务；
- SQL 安全网关和白名单处置；
- 规则评分和报告生成；
- 大模型分级提示、知识解释和报告文字辅助。

教师端第一版仅提供任务记录查看和场景重置，不做知识库、规则和标准答案的完整可视化维护。

### P0-2：三条分支的汇合规则不够严谨

当前文档描述不同起始分支会解锁不同后续任务，但没有明确从“异常日志分析”开始的学员是否仍需完成基线巡检和权限审计。如果允许直接进入备份恢复并汇合，学员可能跳过核心教学任务，与最终验收要求冲突。

**整改要求：**将“分支”定义为任务顺序选择，而不是任务内容的删减。无论从哪个节点开始，进入最终闭环前都必须满足以下状态：

- `baseline_completed = true`；
- `permission_audit_completed = true`；
- `log_analysis_completed = true`；
- `backup_validation_completed = true`；
- 高危发现均已处置或形成合理的保留说明。

建议补充一张状态转移表，明确每个节点的进入条件、完成条件、失败条件、扣分规则和下一节点。

### P0-3：需要强化“智能体”而非普通聊天助手的特征

当前大语言模型主要承担问答、解释和提示，容易被评审人员理解为“Web 教学系统加聊天框”。

**整改要求：**明确智能体的受控工作循环：

> 读取场景状态 → 获取规则检测结果 → 选择只读教学工具 → 组织证据 → 生成分级提示或解释 → 记录教学反馈。

建议第一版限定为以下工具：

1. `get_task_state`：读取当前任务状态；
2. `get_check_result`：读取巡检或规则结果；
3. `get_evidence`：读取脱敏证据；
4. `search_knowledge`：检索课程知识；
5. `submit_hint`：输出分级提示。

所有工具采用固定 JSON 参数和返回结构；模型不持有数据库账号，不接收原始 SQL，不直接改变任务状态，最终评分由规则引擎决定。

### P0-4：验收标准需要量化

现有验收标准大多使用“能够”“可正常完成”等描述，测试时缺少明确的通过条件。

**整改要求：**至少补充以下可测指标：

- 固定场景连续初始化和重置 10 次均成功；
- 场景重置在约定时间内完成，建议不超过 60 秒；
- 预设高危风险的规则识别率达到 100%；
- 未完成四项必做任务时不能生成最终通过报告；
- 所有预设危险 SQL 和越权接口调用均被拒绝并留下审计记录；
- 大模型不可用时，预设提示可支持完成全流程；
- 最终报告的必填字段完整率达到 100%；
- 演示环境从启动到进入场景的时间和普通接口响应时间给出明确上限。

## 5. 建议完善的 P1 问题

### P1-1：补充评分量表

建议采用 100 分制并明确权重，例如：风险发现 30 分、处置正确性 30 分、操作规范 15 分、证据与报告 15 分、时间和提示使用 10 分。危险操作应设置封顶或直接失败规则，避免只扣少量分数。

### P1-2：建立场景真值表

每个模拟事件应配置事件编号、时间、风险对象、证据来源、预期发现、正确处置、严重程度、评分点和重置动作。该真值表应同时驱动日志生成、规则检测、评分和测试，避免四套逻辑不一致。

建议将“攻击回放服务”在界面和答辩中表述为“安全事件场景注入与回放”，突出教学和防守属性。

### P1-3：明确备份恢复的实现口径

第一版建议固定 MySQL 版本，使用小规模逻辑备份样本，在独立恢复库中验证：文件校验值、表结构、记录数量和关键业务校验值。不要把物理备份、时间点恢复和大数据量恢复同时纳入 MVP。

### P1-4：将安全审计前移

安全审计不应只安排在最后一天。建议在接口设计、SQL 网关完成、模型接入和最终打包四个节点分别检查：密钥泄露、SQL 注入、越权访问、日志敏感信息、依赖漏洞、提示词注入和模型越权调用。

### P1-5：补充最小页面与接口清单

开发前至少确定场景主页、任务实操页、证据分析页和报告页四个核心页面，以及场景、任务、规则、证据、提示、评分和重置等核心接口。详细视觉设计可以后补，但演示主路径必须先固定。

## 6. 建议的 MVP 演示路径

1. 启动系统并初始化“公共服务平台数据库异常”场景；
2. 学员选择任一调查起点；
3. 系统注入固定异常账号、日志、权限和备份证据；
4. 学员依次完成四项必做任务，顺序可以不同；
5. 规则引擎校验结果，大模型按当前状态提供解释和分级提示；
6. 学员通过固定接口锁定异常账号、回收过度授权并完成备份恢复验证；
7. 系统生成评分、证据时间线和数据库安全运维报告；
8. 一键重置场景，证明环境可重复演示。

这条路径完整覆盖指导手册要求的“规划—开发—实操—风控—复盘”能力，也足以作为第一版答辩演示。
