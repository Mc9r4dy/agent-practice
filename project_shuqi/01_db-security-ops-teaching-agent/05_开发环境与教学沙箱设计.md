# 数据库安全运维教学智能体——开发环境与教学沙箱设计

## 1. 文档状态

- **设计范围：**开发环境、VS Code 工作区、MySQL 教学沙箱、测试基线和开发日志
- **当前阶段：**环境实施已完成，待 VS Code Dev Containers 人工连接确认
- **设计确认日期：**2026-07-17
- **目标目录：**`F:\project_shuqi\01_数据库安全运维教学智能体`
- **明确排除：**前端业务页面、FastAPI 业务接口、大模型接入、故事状态机和评分功能

本文档只定义第一阶段“可重复启动的开发环境和隔离教学沙箱”。业务功能将在该环境通过验收后另行设计和开发。

## 2. 目标与成功标准

### 2.1 目标

建立一套能够在 Visual Studio Code 中直接使用、由 Docker Compose 统一编排、与本机 MySQL57 完全分离的开发环境。环境应包含 Python、Node.js、MySQL 客户端、测试工具、MySQL 8.4 LTS 教学数据库、合成数据、低权限账号、初始化脚本和重置脚本。

### 2.2 成功标准

1. Docker Desktop 启动后可通过一个命令或一个 VS Code 任务启动全部环境；
2. VS Code 可重新打开到开发容器；
3. 开发容器内提供 Python 3.13、Node.js 24 LTS、Git、MySQL 客户端和测试工具；
4. MySQL 教学沙箱健康检查通过；
5. 教学沙箱只绑定 `127.0.0.1:3307`；
6. 现有 MySQL57、3306 端口及 `E:\MySql` 不被连接、停止或修改；
7. 合成数据、权限快照、日志证据和备份状态能够重复初始化；
8. 低权限账号无法写入业务表或读取 MySQL 系统权限表；
9. 快速重置和完整重建均只作用于本项目容器和数据卷；
10. 环境测试全部通过，失败时提供可定位的错误信息；
11. 每项开发动作同步写入 `04_开发日志.md`，日志中不出现真实秘密。

## 3. 已确认的技术路线

### 3.1 方案选择

采用“VS Code Dev Container + Docker Compose”方案。主机只要求 Docker Desktop、Docker Compose 和 Visual Studio Code，不依赖主机 Python 或 Node.js。

未采用的方案：

- **后端和前端运行在 Windows、仅 MySQL 容器化：**主机 Python 不可用，Node.js 16.12.0 已过旧，容易产生依赖差异；
- **复用本机 MySQL57：**存在误操作既有数据库、端口冲突和版本耦合风险，不满足教学沙箱隔离要求。

### 3.2 固定运行时

| 组件 | 选定版本线 | 选择原因 |
| --- | --- | --- |
| MySQL | 8.4 LTS | 功能稳定、长期支持，适合作为教学基线 |
| Python | 3.13 | 处于官方维护期，适合 FastAPI 和测试工具链 |
| Node.js | 24 LTS | 当前 LTS，避免使用主机已停止支持的 Node.js 16 |
| Docker Compose | 本机 v2.40.3 或兼容的 Compose v2 | 已安装，可编排多容器开发环境 |
| VS Code | 本机 1.124.0 或兼容版本 | 用户指定的开发编辑器 |

镜像在实施阶段固定到明确标签；不得使用 `latest`。

## 4. 总体架构

### 4.1 组件

1. **开发工作区容器 `shuqi-workspace`**
   - 挂载当前智能体项目目录；
   - 提供 Python、Node.js、Git、MySQL 客户端、pytest 和基础开发工具；
   - 供 VS Code Dev Containers 扩展连接；
   - 当前阶段保持常驻，不启动业务服务。

2. **MySQL 教学沙箱 `shuqi-mysql-sandbox`**
   - 运行 MySQL 8.4 LTS；
   - 使用独立命名数据卷；
   - 只读挂载本项目初始化脚本；
   - MySQL 运行参数由 Compose `command` 明确传入，`sandbox.cnf` 仅保留为配置来源说明，避免 Windows bind mount 权限语义导致 MySQL 忽略配置；
   - 暴露到主机 `127.0.0.1:3307`；
   - 提供数据库健康检查。

3. **环境测试入口**
   - 在开发工作区容器内执行；
   - 包含 Compose 静态测试、数据库集成测试、权限测试和重置测试；
   - 测试失败时返回非零退出码。

4. **PowerShell 管理脚本**
   - 面向 Windows 主机提供启动、停止、状态、日志、快速重置、完整重建和测试入口；
   - 每个破坏性动作执行前验证 Compose 项目名、容器名、数据卷名和当前目录。

### 4.2 网络

- `shuqi-dev-net`：开发工作区的普通开发网络；
- `shuqi-sandbox-net`：开发工作区与 MySQL 沙箱之间的内部网络；
- MySQL 沙箱同时加入 `shuqi-dev-net` 和 `shuqi-sandbox-net`；前者用于实现回环端口发布，后者用于容器间教学流量；
- 开发工作区同时加入两个网络，以便后续访问依赖源和大模型接口；
- MySQL 容器不承担网络转发，不配置访问宿主机其他数据库的地址；
- 主机映射使用 `127.0.0.1:3307:3306`，禁止绑定 `0.0.0.0`。

## 6. 教学数据库设计

### 6.1 数据库

教学数据库固定命名为 `shuqi_sandbox`，字符集使用 `utf8mb4`。所有数据均为合成数据，不导入真实个人信息、生产日志或真实凭据。

### 6.2 核心表

| 表名 | 用途 | 数据性质 |
| --- | --- | --- |
| `citizen_profile` | 模拟公共服务平台用户资料 | 合成姓名、证件标识和联系方式 |
| `service_request` | 模拟业务办理记录 | 合成事项、状态和时间 |
| `account_inventory` | 展示正常、异常和长期未用账号 | 教学账号快照，不映射生产账号 |
| `permission_snapshot` | 展示账号、来源、对象和权限关系 | 教学授权快照 |
| `web_access_log` | 提供异常请求和来源证据 | 预设日志文本，不可执行 |
| `db_audit_log` | 提供登录、查询和敏感表访问证据 | 预设审计事件 |
| `backup_catalog` | 展示备份时间、大小、校验值和可用状态 | 合成备份元数据 |
| `scenario_event` | 统一记录固定事件时间线 | 场景真值与证据关联 |
| `scenario_state` | 保存当前场景版本和重置标识 | 环境验证状态 |

### 6.3 教学视图

- `v_account_audit`：展示账号风险、来源范围和最后活动时间；
- `v_permission_audit`：展示过度授权和高风险权限；
- `v_suspicious_activity`：关联 Web 请求、数据库查询和账号；
- `v_backup_status`：展示备份完整性和恢复可用性。

低权限学员账号优先访问视图，不直接访问系统表。

### 6.4 模拟事件

第一阶段只预置一个固定场景：公共服务平台数据库出现异常账号、过度授权、可疑查询和备份异常。

SQL 注入仅表现为：

- 脱敏后的异常请求片段；
- 与请求时间相对应的数据库查询摘要；
- 风险标签和预期处置；
- 不可直接执行的教学证据。

初始化脚本不包含可用于外部目标的自动攻击程序，不开放任意载荷参数。

## 7. 数据库账号与权限

### 7.1 账号

1. **`sandbox_reader`**
   - 供教学查询和集成测试使用；
   - 只能 `SELECT` 指定教学视图；
   - 不能写表、创建对象、管理用户或读取 MySQL 系统权限表。

2. **`sandbox_app`**
   - 供后续 FastAPI 后端使用；
   - 第一阶段只获得读取教学数据和更新受控场景状态所需的最小权限；
   - 不具有建库、删库、用户管理或全局权限。

3. **`root`**
   - 仅用于容器内部初始化、健康检查所需配置和受控重置；
   - 不创建允许主机远程登录的 root 账号；
   - root 密码只存在于本地 `.env` 和容器环境，不写入源码或开发日志。

### 7.2 异常账号的模拟方式

教学故事中的异常高权限账号保存在 `account_inventory` 和 `permission_snapshot` 中，不创建为具有真实高权限的 MySQL 登录账号。学员对异常账号的“锁定”和“权限回收”在场景数据层完成，避免向学员开放 MySQL 用户管理权限。

## 8. 环境变量与秘密管理

- 提供 `.env.example`，只包含变量名和非秘密说明；
- 实际 `.env` 在首次 Start 时由本地初始化流程自动生成；若已存在则复用，不覆盖用户已有本地秘密；
- `.gitignore` 必须忽略 `.env`、数据库数据、测试缓存、日志导出和 IDE 临时文件；
- 脚本输出使用脱敏连接信息，例如 `mysql://sandbox_reader:<redacted>@127.0.0.1:3307/shuqi_sandbox`；
- 开发日志不得记录密码、令牌、API 密钥或完整秘密连接串；
- 自动生成的 3 个密码各使用 24 字节密码学随机数并编码为 48 位十六进制；不使用生产默认值或空密码继续启动。

## 9. 启动、停止与重置

### 9.1 启动流程

1. 确认当前目录为本智能体项目目录；
2. 确认 Docker Desktop 守护进程可用；
3. 确认 3307 未被其他进程占用；
4. 若 `.env` 不存在则生成随机本地秘密；若存在则由 Compose 验证必要变量；
5. 解析 Compose 配置；
6. 构建开发工作区镜像；
7. 启动 MySQL 沙箱并等待健康检查；
8. 启动开发工作区；
9. 输出 Compose 容器、健康状态和端口信息；
10. 由独立 Test 动作执行静态、数据和权限集成测试。

任何一步失败都停止后续步骤，不回退连接到本机 MySQL57。

### 9.2 停止

停止操作只停止当前 Compose 项目中的容器，默认保留教学数据卷。停止前后均记录目标容器和执行结果。

### 9.3 快速重置

快速重置只重放 `shuqi_sandbox` 中的标准合成种子数据，不删除容器或数据卷，也不修改表、视图和账号定义。预期在 60 秒内完成；验收流程在重置后运行完整测试。

### 9.4 完整重建

完整重建用于初始化损坏或版本变更。脚本必须先验证：

- 当前目录匹配本项目；
- Compose 项目名为固定值；
- 目标容器和数据卷名称带有 `shuqi` 前缀；
- 目标不包含现有 MySQL57 路径或服务名。

验证通过后才允许删除当前项目容器和命名数据卷，再重新构建。脚本不得执行通配删除，不得清理其他 Docker 项目。

## 10. 错误处理

| 错误 | 处理方式 | 禁止行为 |
| --- | --- | --- |
| Docker Desktop 未运行 | 终止并提示启动 Docker Desktop | 不尝试修改其他容器运行时 |
| 3307 被占用 | 显示占用进程并终止 | 不自动结束进程，不自动改用 3306 |
| `.env` 缺失 | Start 自动生成 3 个独立随机密码；Preflight 不创建 `.env` | 不使用空密码，不输出生成值 |
| Compose 配置无效 | 输出配置错误并终止 | 不带错误继续启动 |
| MySQL 健康检查失败 | 输出沙箱容器日志和状态 | 不连接本机 MySQL57 |
| 初始化脚本失败 | 保留容器日志，标记环境不可用 | 不忽略失败表或权限 |
| 权限测试失败 | 阻止验收，保留测试证据 | 不降低测试标准 |
| 重置目标校验失败 | 拒绝删除或重建 | 不执行模糊或通配删除 |

## 11. 测试设计

### 11.1 测试先行原则

环境行为通过自动化测试定义。对于可执行脚本和校验逻辑，先编写失败测试并确认失败原因，再实现最小功能使测试通过。纯 Docker、Compose 和 SQL 配置通过静态断言与集成测试共同验证。

### 11.2 静态配置测试

1. Compose 项目只包含预期服务；
2. MySQL 镜像固定为 8.4 LTS 标签，不使用 `latest`；
3. 端口映射必须是 `127.0.0.1:3307:3306`；
4. 不出现 `privileged: true`；
5. MySQL 数据卷使用命名卷，不挂载 `E:\MySql`；
6. 初始化脚本以只读方式挂载；
7. `.env` 位于 `.gitignore`；
8. Compose 配置不包含明文真实秘密。

### 11.3 数据库集成测试

1. MySQL 健康检查通过；
2. `shuqi_sandbox` 存在且字符集正确；
3. 所有核心表和教学视图存在；
4. 合成数据记录数与预期一致；
5. 场景事件能够关联账号、日志、权限和备份证据；
6. `sandbox_reader` 能查询允许的教学视图；
7. `sandbox_reader` 的 `INSERT`、`UPDATE`、`DELETE` 和 DDL 操作被拒绝；
8. `sandbox_reader` 无法读取 `mysql.user`；
9. `sandbox_app` 无全局管理权限；
10. 日志和报告输出不包含数据库密码。

### 11.4 重置测试

1. 人为修改一条允许修改的场景状态；
2. 执行快速重置；
3. 验证状态和种子数据恢复；
4. 连续执行两次快速重置；
5. 验证两次结果一致；
6. 验证重置总耗时不超过 60 秒；
7. 验证 MySQL57 服务仍处于运行状态且 3306 监听未被本项目改变。

### 11.5 验收证据

验收时保留：

- Docker 和 Compose 版本；
- `docker compose config` 通过结果；
- 容器健康状态；
- 全部测试名称、通过数量和总耗时；
- 端口监听结果；
- 重置前后数据校验结果；
- MySQL57 服务未受影响的只读检查结果。

验收证据写入开发日志，但密码和令牌必须脱敏。

- 操作前状态与判断依据；
- 实际执行的命令或文件操作；
- 变更文件及变更原因；
